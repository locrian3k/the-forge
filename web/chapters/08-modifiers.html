Chapter 8: Modifiers

Primer: Modifiers

Controlling Access and Behavior

Modifiers are keywords you put before a function or variable to control who can use it and how it behaves. Think of them as permission labels:

ModifierWho can access
publicAnyone, from anywhere
protectedThis file + child objects
staticNo external call_other(), but children can access
privateOnly this file, not even children

Three more modifiers handle special cases:

  • nosave, variable is excluded from save/restore (runtime-only data)
  • varargs, function accepts fewer arguments than declared
  • nomask, children cannot override this function

Read the Modifiers chapter of the primer before starting.

Exercise 8.1: Access Control Apprentice

Create an object that demonstrates LPC access modifiers and explain why each modifier is appropriate.

Requirements

  • Create a public function query_title(), callable from any other object via call_other
  • Create a private helper format_name(string name), only callable internally, not from outside or from children
  • Create a protected function internal_reset(), accessible to children but not external objects
  • Create a static function do_setup(), cannot be called via call_other(), but children can call it
  • Each function must have a comment block explaining why that modifier is appropriate
  • create() should call do_setup() to initialize the object

File to create: exercises/ch08_modifiers/ex01_access_control.c

Hints (click to reveal)
  1. Think about who needs to call each function: everyone (public), only this file (private), this file and children (protected), or everything except call_other (static).
  2. private functions cannot be called by children at all. Use protected when children need access.
  3. static on a function means it cannot be reached via call_other(), but children CAN still call it directly.
  4. Understand that format_name is private, meaning external call_other() calls like call_other(obj, "format_name", "test") would be rejected by the driver. Only code inside the same file can call a private function.

Exercise 8.2: Nosave and Varargs Journeyman

Create an object that demonstrates the nosave, varargs, and nomask modifiers.

Requirements

  • Declare nosave int visit_count, increments on each call to do_visit(), resets to 0 on reload
  • Declare a regular string location variable set in create() for contrast
  • Implement varargs string do_announce(string who, string msg, int volume):
    • Works with 1, 2, or 3 arguments
    • If msg is not provided, default to "has arrived"
    • If volume is not provided, default to 1
    • Return a formatted announcement string including all three values
  • Implement nomask string query_id(), returns a fixed identifier that children cannot override
  • Implement int do_visit(), increments and returns visit_count
  • Implement int query_visit_count(), returns the current count

File to create: exercises/ch08_modifiers/ex02_nosave_varargs.c

Hints (click to reveal)
  1. nosave goes before the type: nosave int visit_count;. The variable works normally in memory but is excluded from save/restore.
  2. For varargs, declare as varargs string do_announce(...). Check if (!msg) to apply defaults.
  3. nomask means "cannot be overridden." If a child tries to define the same function, the driver throws a compile error.
  4. The nosave modifier means the variable only exists in memory. If the object were destructed and re-cloned, the counter would reset to 0 because nosave variables are not preserved across object lifetimes.

Capstone Connection: Phase 1 — The Foundation

Modifiers protect your code's internal logic. In your capstone area, private helpers will keep implementation details hidden, nosave variables will track runtime state like spawn timers, and varargs will make your utility functions flexible.
