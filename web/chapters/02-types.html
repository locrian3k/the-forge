Chapter 2: Types

Primer: LPC Types

The Core Idea

A type tells the compiler what kind of data a variable holds. When you write int hp = 100;, the compiler knows hp is a number. When you write string name = "Steve";, it knows name is text. Get the type wrong and the compiler stops you before your code ever runs, that is what #pragma strong_types enforces.

For 95% of MUD coding, you only need five types:

TypeWhat it storesExample
intWhole numbersint hp = 100;
stringTextstring name = "Goblin";
objectGame entitiesobject player = this_player();
statusTrue/false (1/0)status door_open = 1;
mixedAny typemixed x = "could be anything";

Type-checking efuns (built-in functions provided by the driver) like intp(), stringp(), and objectp() let you inspect types at runtime, essential when working with mixed variables. Explicit casting with (int) or (string) converts between types when needed.

Read the Types chapter of the primer before starting.

Exercise 2.1: Type Declaration Drill Apprentice

Create an object that declares one global variable of each basic LPC type and provides query functions to read them.

What You Will Build

This file builds on the structure you learned in Chapter 1 (file header comment, pragma, include, inherit, create). It adds two new ideas: global variables and query functions.

1. Preamble (same as Chapter 1)

Start with the file header comment, pragma, include, and inherit, exactly like Exercise 1.1:

/*
  ex01_declare_types.c
  YourName YYMMDD
  Exercise 2.1, one variable of each LPC type.
*/
#pragma strong_types
#include "defs.h"

inherit "obj/treasure";

2. Global Variables (new concept)

A global variable is declared outside of any function, between the inherit line and the first function. It belongs to the whole object, every function in the file can read it and change it, and it persists for the lifetime of the object.

The syntax is the type, then the variable name, then a semicolon:

int score;
status active;
string label;

Notice there is no = here. Global variables start with a default value of 0 (null) for all types — numbers, strings, objects, and status alike. An uninitialized string is 0, not "" (empty string). You will give them real values inside create().

You need six global variables, one of each type:

TypeVariable nameWhat it stores
intscoreA whole number (e.g. 42)
statusactiveTrue or false (1 or 0)
stringlabelText (e.g. "Hello from The Forge")
floatratioA decimal number (e.g. 3.14)
objectselfA reference to a game entity
mixedwildcardAnything, the compiler does not check it

3. The create() Function

Inside create(), do three things (in this order):

  1. Call ::create(); so the parent treasure initializes.
  2. Set the object identity using the setters you learned in Chapter 1:
    • set_name("type sampler");
    • set_short("a type sampler");
    • Set a long description, aliases, value, and weight of your choice.
  3. Assign values to your global variables. To assign a value to a variable, use the = operator. Each assignment is a statement that ends with a semicolon: 
      score = 42;
  active = 1;
  label = "Hello from The Forge";
  ratio = 3.14;
  self = this_object();
  wildcard = "I could be anything";

    Key details:

    • status values are only ever 1 (true) or 0 (false).
    • float literals must have a decimal point: 3.14, not 3.
    • this_object() is a built-in function that returns a reference to the current object. It is the simplest way to get a valid object value.
    • mixed can hold anything, a string, an int, an object. The compiler will not check what you put in it.

End create() with return; as always.

4. Query Functions (new concept)

In Chapter 1, your create() was a void function, it does work but does not hand a value back to its caller. A query function is different: it returns a value. Other code in the game calls your query function to read data from your object.

Here is the pattern:

int query_score() { return score; }

Breaking this down piece by piece:

  • int, the return type. This tells the compiler "this function hands back a whole number."
  • query_score, the function name. On 3K, functions that read data always start with query_.
  • (), empty parentheses mean it takes no arguments.
  • { return score; }, the body. return sends the value of score back to whatever called this function. The semicolon ends the statement. The braces wrap the body.

Because the body is just a single return statement, 3K codestyle allows writing the entire function on one line, signature, braces, and body all together. The braces { } are still there, they just stay on the same line instead of using Allman style (where the opening { would go on its own line). This is the only time the same-line brace style is used.

The return type must match the variable type. If the variable is a string, the function's return type must be string: 

string query_label() { return label; }

Write one query function for each of your six global variables:

  • int query_score(), returns score
  • status query_active(), returns active
  • string query_label(), returns label
  • float query_ratio(), returns ratio
  • object query_self(), returns self
  • mixed query_wildcard(), returns wildcard

These go after create(), at the bottom of the file.

Requirements Summary

  • File header comment, #pragma strong_types, #include "defs.h"
  • inherit "obj/treasure";
  • Six global variables: int score, status active, string label, float ratio, object self, mixed wildcard
  • A void create() that calls ::create();, sets the object's name to "type sampler", short to "a type sampler", and assigns a value to each global variable
  • Six one-line query functions, each returning the matching variable with the correct return type
  • All 3K codestyle rules (2-space indent, Allman brackets for multi-line functions, return; at end of create())

File to create: exercises/ch02_types/ex01_declare_types.c

Compare: ex01_declare_types_solution.c

Hints (click to reveal)
  1. A common mistake is mismatching the return type on a query function — make sure each function's return type matches the variable it returns. int variable → int function, string variable → string function, etc.
  2. Global variables go between inherit and create(). If you declare them inside create(), they become local variables (Chapter 3 explains the difference) and your query functions will not be able to see them.
  3. One-line query functions use braces on the same line: int query_score() { return score; }. This is the only exception to Allman bracket style in 3K codestyle.
  4. Do not forget return; at the end of create(). The query functions already have their own return statements with values.

Exercise 2.2: Type Conversion Journeyman

Write an object with utility functions that convert between LPC types.

What You Will Build

In Exercise 2.1 you wrote query functions that take no arguments. This exercise introduces functions with parameters, functions that accept input, do something with it, and return a result.

Functions That Take Arguments

In Exercise 2.1, your query functions looked like int query_score() — empty parentheses, no input. Now you will write functions that receive a value from their caller. The value goes inside the parentheses with its type: 

string int_to_string(int n)
{
  // n is an integer that was passed in by the caller.
  // Do something with it and return a result.
}

Breaking this down:

  • string, the return type. This function hands back text.
  • int_to_string, the function name.
  • int n, the parameter. When someone calls int_to_string(42), the value 42 is stored in n for the duration of that function call.

Since these functions have multiple lines, use Allman brackets (opening { on its own line) just like create().

Type Casting

Sometimes you need to convert a value from one type to another. In LPC, you can cast a value by putting the target type in parentheses before it: 

(string)42       // converts the int 42 into the string "42"
(int)"7"         // converts the string "7" into the int 7

This is called a typecast. Not all conversions work, you cannot cast an array into an integer, for example, but between the basic types it usually does what you expect.

Type-Checking Efuns

LPC provides built-in functions that test what type a value is. Each returns 1 (true) or 0 (false):

  • intp(x), is x an integer?
  • stringp(x), is x a string?
  • floatp(x), is x a float?
  • objectp(x), is x an object?

These are essential when working with mixed variables, because the compiler cannot check the type for you, you have to check at runtime.

Requirements

Start with the standard preamble (file header comment, pragma, include) and inherit "obj/treasure";. In create(), set the name to "type converter" and short to "a type converter". Then write these four functions:

string int_to_string(int n)

Takes an integer and returns it as a string. For example, if n is 42, return "42".

int string_to_int(string s)

Takes a string and returns it as an integer. For example, if s is "7", return 7. If the string does not start with digits (e.g. "abc"), return 0.

status status_check(int n)

Takes an integer and returns 1 if it is greater than 0, otherwise returns 0.

string describe_type(mixed val)

Takes a mixed value and returns a string naming its type: "int", "string", "float", "object", or "unknown". Use the type-checking efuns listed above to figure out which type it is.

File to create: exercises/ch02_types/ex02_type_conversion.c

Compare: ex02_type_conversion_solution.c

Hints (click to reveal)
  1. int_to_string: The cast (string)n converts an int to a string. Alternatively, "" + n also works, adding an int to a string produces a string.
  2. string_to_int: The cast (int)s converts a string to an integer. "42abc" becomes 42; "abc" becomes 0. This handles the "no digits" case automatically.
  3. status_check: The comparison n > 0 already produces a 1 or 0 result. You can return it directly: return n > 0;
  4. describe_type: Use if statements to test each type in order. You have not formally learned if yet (that is Chapter 7), but the pattern is: if (intp(val)) return "int";. Check int, string, float, and object. If none match, return "unknown".

Capstone Connection: Phase 1 — The Foundation

Understanding types is critical for every object in your dungeon. Monster stats are integers, descriptions are strings, item references are objects. Getting comfortable with the type system now prevents a whole class of bugs later.
