Chapter 0: The Big Picture

Primer: 3K Code Primer

Before diving into syntax, it helps to understand how LPC thinks. This page gives you the mental models that make everything else in this curriculum click.

Know Your Folders

The Starter Package you downloaded from the Home page is organized into folders you will work with throughout the curriculum:

  • exercises/ — Starter files with TODO comments for you to fill in. Each chapter has its own subdirectory (e.g., exercises/ch01_intro/). Open these in your text editor and write your code.
  • solutions/ — Fully commented reference implementations. When you finish an exercise, compare your work against the matching solution file.
  • reference/ — Quick-reference cheatsheets you can look up while working.
  • capstone/ — A multi-phase final project where you build a complete dungeon area. Templates and phase guides are inside.

The exercises/ folder contains a defs.h file. This is a shared header that defines common shortcuts used across all exercises. You do not need to create or modify it, just know that when your code says #include "../defs.h", it pulls in those shortcuts automatically. Chapter 1 explains what is inside it.

Everything is an Object

In LPC, literally everything in the game world is an object - players, monsters, rooms, swords, armor, NPCs, even daemon processes that run behind the scenes. Each object is a file on disk (a .c file) that the driver loads into memory when something needs it.

Here is how LPC organizes the game world: 

LPC Game World
│
├─ Objects (everything in the game)
│   ├─ players
│   ├─ monsters
│   ├─ rooms
│   └─ items (weapons, armor, treasure)
│
├─ Data Types (what objects store)
│   ├─ int        → numbers
│   ├─ string     → text
│   ├─ object     → game entities
│   ├─ array      → lists
│   └─ mapping    → dictionaries
│
├─ Functions (behavior)
│   ├─ create()     → initialize
│   ├─ attack()     → combat
│   └─ query_name() → data access
│
└─ Driver (the game engine that runs it all)

Each object has two things: variables (data it stores) and functions (things it can do). Think of every object as a little machine with its own memory and its own set of buttons: 

object
│
├─ variables
│   hp
│   name
│   level
│
└─ functions
    attack()
    die()
    move()

A sword object stores its damage and name. A monster object stores its hit points and attack patterns. A room object stores its description and exits. Same structure, different data.

Objects Know Where They Are

Every object has an environment, the object that contains it. This creates a containment tree that models the entire game world: 

Room
└─ Player
    ├─ Sword
    ├─ Shield
    └─ Gold Ring

The room contains the player. The player contains the sword, shield, and ring. In code:

  • environment(player) returns the room
  • environment(sword) returns the player
  • all_inventory(player) returns everything the player is carrying

This containment model is how LPC knows what is where. When you pick up an item, it moves from the room's inventory into the player's inventory. When you enter a room, your player object moves into that room object.

How Objects Find Each Other

Four functions you will use constantly to locate objects in the game:

  • this_player(), who typed the command (the player who triggered this code)
  • this_object(), the object whose code is currently running (abbreviated TO in defs.h)
  • environment(), where something is located (its container)
  • present("sword", player), find an object by name inside a container

These are your navigation tools. Almost every function you write will start by using one or more of these to find the objects it needs to work with.

How Objects Talk to Each Other

Objects communicate by calling functions on each other using the -> operator (called the "call other" operator): 

player->query_name()    // ask the player their name
monster->add_hp(-10)    // damage the monster
room->tell_room("...")  // send a message to the room

This is the core skill of LPC programming: find the right object, call the right function on it.

You do not need to know how a monster tracks its HP internally. You just call monster->add_hp(-10) and the monster handles the rest. This is why LPC is built around objects, each one manages its own complexity.

The Driver: How Code Actually Runs

The driver is the game engine. It is the C program that loads your LPC files, compiles them, and runs them. It manages an event loop that keeps the game world ticking: 

Driver Event Loop
│
├─ Player commands    → parsed and executed immediately
├─ Combat rounds      → automatic attacks on a timer
├─ Heartbeats         → heart_beat() called every ~2 seconds
├─ Scheduled events   → call_out() fires after a delay
├─ Object creation    → clone_object() loads files into the game
└─ Reset cycle        → reset() called periodically for respawning

When a player types a command like kill goblin, here is what happens:

  1. The driver receives the input from the player's connection
  2. It finds the matching command function (registered with add_action())
  3. That function runs, interacting with other objects as needed
  4. Messages are sent to the relevant players in the room

You do not write the driver or the event loop. You write the objects that the driver runs. Your job is to define what happens when the driver calls your functions.

The Five Types That Matter

For 95% of MUD coding, you only need five data types:

Type What it stores Example
int Numbers int hp = 100;
string Text string name = "Goblin";
object Game entities object player = this_player();
array Lists string *pets = ({"dog","cat"});
mapping Dictionaries mapping scores = (["Steve":5]);

Everything else (float, status, mixed, closure) is either rare or specialized. You will learn them when you need them.

The Eight Patterns You Will See Everywhere

Pattern 1: Query/Set Functions

Objects expose data through getter functions like query_name() and query_level(), and configure themselves through setters like set_name() and set_level(). You never access another object's variables directly from outside, always go through the functions.

Pattern 2: Inheritance

Most objects inherit from a base class. Writing inherit "obj/monster"; gives you all the default monster behavior, HP tracking, combat, movement, death. Your file only adds what is different. This is how you avoid writing thousands of lines for every monster.

Pattern 3: create()

Every object's create() function runs once when the object is first loaded. It calls ::create() (the parent's version) first, then configures the object with setter calls. This is where you define what makes your object unique.

Pattern 4: init()

Called when a living thing enters the object's environment. Used to register commands with add_action(). For example, a room uses init() to add special commands that only work in that room.

Pattern 5: reset()

Called periodically by the driver (usually every few minutes). Used to respawn monsters and restock items. If a room's guardian monster has been killed, reset() creates a new one.

Pattern 6: Messaging

tell_object(player, "You feel cold.") sends a message to one player. tell_room(room, "A goblin enters.", player) sends a message to everyone in the room except the specified player. These are how the game communicates what is happening.

Pattern 7: Object Movement

move_object(item, player) puts an item in a player's inventory. clone_object("/obj/sword") creates a new instance of a sword. destruct(obj) removes an object from the game entirely.

Pattern 8: Safety Checks

Always check before using an object reference: if (!objectp(obj)) return; prevents crashes when an object might have been destroyed between when you found it and when you try to use it. This is a habit you will build early and use forever.
