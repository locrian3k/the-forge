Chapter 1: Introduction

Primer: Introduction to LPC

Every LPC file on 3Kingdoms follows a strict structure: it begins with an optional file header comment (filename, author, date), then #pragma strong_types and #include "defs.h", followed by an inherit statement that tells the driver which parent object to build on. The create() function runs once when the object is first loaded, and it always calls ::create() to let the parent initialize first.

These exercises get you writing your first LPC file and training your eye for the structural rules that every 3K file must follow. If you can write a compilable object and spot common bugs, you are ready to move on.

Read the Introduction chapter of the primer before starting.

Before You Begin: What is defs.h?

Every LPC area on 3Kingdoms uses a header file called defs.h. Think of it as a shared cheat-sheet: it defines shortcuts (called "macros") that you can reuse across all your files instead of typing out long paths or common patterns every time.

For example, instead of writing this_object() everywhere, the header lets you write TO. Instead of typing the full path to your area's monsters directory, you define it once in defs.h and reuse the shortcut.

A defs.h file is already included in each exercise directory. Open exercises/ch01_intro/defs.h to see what is inside: 

// Minimal header for Forge curriculum exercises.
// You will build a full area defs.h in Chapter 9 and Chapter 18.

#define TO        this_object()
#define TP        this_player()
#define ETO       environment()

That is it for now, just three shortcuts. You will learn exactly how #define and #include work in Chapter 9 (Preprocessor). For now, just know that when your code says #include "defs.h", it copies the contents of that file into yours at compile time.

When you become a wizard on the MUD, your exercise files would live at /players/<yourname>/exercises/ and this same defs.h pattern carries over.

Exercise 1.1: Hello Mud Apprentice

Write your very first LPC object: a simple training stone that a player could pick up and examine.

What You Will Build

The finished file has five sections, in this exact order:

1. File Header Comment

Every file starts with a block comment identifying it:

/*
  filename.c
  YourName YYMMDD
  Brief description of what this file does.
*/

Replace YourName with your character name and YYMMDD with today's date (e.g., 260315 for March 15, 2026).

2. Preamble

Two lines that every .c file on 3K must have, right after the comment: 

#pragma strong_types
#include "../defs.h"

#pragma strong_types tells the compiler — the part of the MUD driver that reads your LPC code and turns it into something the game can run — to enforce type checking, meaning it will catch mistakes like putting text where a number is expected. You will learn about types in Chapter 2. #include "../defs.h" pulls in the shared header file from the exercises/ folder. The ../ means "go up one directory", since your exercise file is inside exercises/ch01_intro/, the ../ takes you back up to exercises/ where defs.h lives. On a live MUD, areas typically use #include "defs.h" because the header is in the same directory as the code.

3. Inherit Statement

This tells the driver your object is built on top of an existing parent object. The syntax is the keyword inherit, followed by the path to the parent in quotes, ending with a semicolon: 

inherit "obj/treasure";

This means your object gets all the behavior of a treasure (it can be picked up, dropped, examined, etc.) without you having to write that code yourself.

4. The create() Function

create() is the function the driver calls once when your object is first loaded into the game. You define it like this: 

void create()
{
  // your code goes here

  return;
}

Key syntax details:

  • void means this function does not return a value to its caller.
  • create is the function name. The parentheses () after it mean it takes no arguments.
  • The opening brace { goes on its own line (this is called Allman bracket style).
  • Every line inside the function is indented by 2 spaces (not tabs).
  • The function must end with return;, note the semicolon.

5. What Goes Inside create()

Inside create(), you need to do several things. Every statement ends with a semicolon (;).

First, call the parent's create function so the treasure initializes properly: 

  ::create();

The :: means "call the version of this function defined in my parent."

Then, use setter functions to configure your object. Each setter takes one argument in parentheses:

  • set_name("training stone");, the internal name the game uses to identify your object (what players type to interact with it)
  • set_alias(({"stone", "training stone"}));, alternate names players can use. The ({"...", "..."}) syntax is an LPC array. Note the double parentheses: the outer () belong to the function call, the inner ({...}) is the array.
  • set_short("a training stone");, the one-line description shown in room inventories and when picking things up
  • set_long("Your description here.");, the full description shown when a player examines the object. Write a sentence or two.
  • set_value(10);, how many coins the object is worth
  • set_weight(1);, how heavy the object is

Requirements Summary

  • File header comment (filename, your name, date, description)
  • #pragma strong_types as the first non-comment line
  • #include "defs.h" or #include "../defs.h"
  • inherit "obj/treasure";
  • A void create() function with Allman brackets that:
    • Calls ::create();
    • Sets name to "training stone"
    • Sets aliases to ({"stone", "training stone"})
    • Sets short to "a training stone"
    • Sets long to a description you write
    • Sets value to 10
    • Sets weight to 1
    • Ends with return;
  • 2-space indentation (spaces only, no tabs)

Hints (click to reveal)
  1. Every statement must end with a semicolon — missing one would cause a compile error on the MUD. Double-check ::create(); and return;.
  2. Make sure your opening braces { are each on their own line, not on the same line as void create().
  3. The alias array uses LPC array syntax: ({"item1", "item2"}). If you forget the ({ and }) wrappers, the code would not compile on the MUD.
  4. Your long description can be any text you like. Just make sure it is wrapped in double quotes and ends with a semicolon.

Exercise 1.2: Anatomy of an LPC File Journeyman

Find and fix every bug in a broken LPC file. Train your eye for the structural rules every 3K file must follow.

The Broken File

The file below is supposed to be a working treasure object, but it has 8 bugs that violate 3K codestyle or will prevent it from compiling. Open ex02_anatomy.c, then find and fix all 8 issues.

Use what you learned in Exercise 1.1 about file structure, bracket style, indentation, types, and statement endings to guide your review. 

#include <defs.h>

inherit "obj/treasure";

void create()  {
	::create();

	set_name("broken gem");
	set_alias(({"gem", "broken gem"}));
	set_short("a broken gem");
	set_long("A gemstone riddled with cracks. Something is wrong with it.");
	set_value(5);
	set_weight(1);

	return
}

Requirements

  • Find and fix all 6 bugs
  • The fixed file should have no syntax errors that would prevent compilation
  • The fixed file must follow all 3K codestyle rules from Exercise 1.1
  • Do not change the object's name, descriptions, value, or weight, only fix the structural and style issues

Tip: Read the file top to bottom, line by line. Compare each section against the structure you learned in Exercise 1.1. Some bugs will prevent compilation; others are style violations you can spot by comparing against the rules from Exercise 1.1.
