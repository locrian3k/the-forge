Chapter 10: Inheritance

Primer: Inheritance

Building on What Already Exists

Inheritance is the reason you can create a working monster in 20 lines instead of 2,000. When you write inherit "obj/monster";, your object gets all of the monster class's functions, movement, combat, chat, death handling — for free. Your file only adds what is different. 

Parent: /obj/monster
│  set_name(), set_level(), attack(), die(), ...
│
└─ Your file: goblin.c
    create() → sets name, level, chat messages
    (everything else inherited automatically)

The :: Operator

::create() means "call my parent's version of create." In create(), you always call ::create(); first so the parent initializes before you customize. When overriding other functions, calling ::function_name() lets you extend behavior rather than replace it.

Multiple Inheritance

LPC supports inheriting from two or more parents simultaneously. The child gets functions from all parents. When parent names collide, you specify which one: describable::create();

Read the Inheritance chapter of the primer before starting.

Exercise 10.1: Basic Inheritance Apprentice

Create a base class and a child class that inherits from it.

File 1: ex01_base_creature.c

  • Declare a global string creature_name
  • Implement create() that sets creature_name to "creature"
  • Implement query_creature_name() returning creature_name
  • Implement set_creature_name(string s) that sets creature_name

File 2: ex01_goblin.c

  • Inherit ex01_base_creature.c
  • Implement create() that calls ::create() first, then set_creature_name("goblin")
  • Implement query_battle_cry() returning a goblin war cry string
  • Implement query_description() using query_creature_name() from the parent

Files to create: exercises/ch10_inheritance/ex01_base_creature.c and exercises/ch10_inheritance/ex01_goblin.c

Hints (click to reveal)
  1. The inherit statement goes after #include but before any globals: inherit "path/to/ex01_base_creature";
  2. ::create() calls the parent's version of create(). Always call this first so the parent initializes before you customize.
  3. The child automatically has access to query_creature_name() and set_creature_name() without re-implementing them.
  4. You can call inherited functions just like local ones, the child "is a" base_creature.

Exercise 10.2: Override and Extend Journeyman

Override a parent function in a child class while still calling the parent's version.

File 1: ex02_base_npc.c

  • Implement extra_look() returning a base description, e.g. "This is a generic NPC."
  • Implement query_greeting() returning a base greeting, e.g. "Hello there."
  • Implement create() with basic setup

File 2: ex02_guard.c

  • Inherit ex02_base_npc.c
  • Override extra_look(), call ::extra_look() to get the parent's text, then concatenate guard-specific text
  • Override query_greeting() similarly, call ::query_greeting() then append guard dialogue
  • Implement query_post() returning the guard's assigned post
  • Call ::create() in the child's create()

Files to create: exercises/ch10_inheritance/ex02_base_npc.c and exercises/ch10_inheritance/ex02_guard.c

Hints (click to reveal)
  1. To call the parent version of an overridden function, prefix with ::, e.g. ::extra_look().
  2. String concatenation: ::extra_look() + "\nExtra text." builds on the parent's output.
  3. The key concept: overriding replaces the function, but :: lets you still access the original. This is "extend" vs. "replace."
  4. If you forget ::create() in the child, the parent's initialization never runs.

Exercise 10.3: Multiple Inheritance Journeyman

Create an object that inherits from two separate parent classes.

File 1: ex03_describable.c

  • Declare a global string description
  • Implement create() that sets description to a default
  • Implement query_description() and set_description(string s)

File 2: ex03_trackable.c

  • Declare a global string location
  • Implement create() that sets location to a default
  • Implement query_location() and set_location(string s)

File 3: ex03_artifact.c

  • Inherit both ex03_describable.c and ex03_trackable.c
  • Implement create() that calls both parent creates: describable::create() and trackable::create(), then sets custom values
  • Implement query_full_info() combining query_description() and query_location()
  • Implement query_artifact_name() returning the artifact's name

Files to create: exercises/ch10_inheritance/ex03_describable.c, exercises/ch10_inheritance/ex03_trackable.c, and exercises/ch10_inheritance/ex03_artifact.c

Hints (click to reveal)
  1. Multiple inherit statements stack: 
    inherit "path/to/ex03_describable";
inherit "path/to/ex03_trackable";
  2. When both parents have create(), a plain ::create() calls only the first parent's. Use the named form: describable::create() and trackable::create().
  3. The child has ALL functions from BOTH parents, you can call query_description() and query_location() as if they were local.
  4. Watch for name collisions. In this exercise the parents have different function names (except create()), so the only conflict is the dual create call.

Capstone Connection: Phase 2 — Atmosphere

Inheritance is the architectural backbone of your capstone dungeon. Rooms inherit from /room/room or dungeon room bases, monsters inherit from /obj/monster, and weapons inherit from /obj/weapon. Every game object you build in the capstone uses inheritance to specialize a parent class with your custom behavior.
