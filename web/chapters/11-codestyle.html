Chapter 11: Code Style

Read the primer: Code Style

Why Style Matters

Consistent code style is not cosmetic, it is how a team of builders can open any file in a MUD codebase and immediately understand its structure. On 3Kingdoms, every builder follows the same conventions.

The Rules at a Glance

RuleExample
File header comment first/* file.c / Author YYMMDD / Description */
#pragma strong_types first non-comment line
Spaces only, 2-space indentNo tabs ever
Allman brackets{ on its own line
status for booleansNot int
Explicit return;End of every void function
lowercase_underscore namingquery_name(), do_attack()

These exercises give you practice spotting and correcting style violations, a skill you will use every time you write or review LPC code.

Read the Code Style chapter of the primer before starting.

Tip: If you use Visual Studio Code, the 3K Codestyle for LPC extension catches these style violations as you type and can auto-format your code to match 3K conventions. It checks all the rules in the table above automatically.

Exercise 11.1: Style Correction Apprentice

Identify and fix all codestyle violations in a broken LPC room file.

The following room file compiles but violates 3K codestyle in many ways. Copy it into your exercise file, then fix every violation you can find.

#include "defs.h"

inherit "room/room";

int isLit;
string longDescription;

void create() {
	set_short("A dusty storeroom");
	longDescription = "You stand in a cramped storeroom.  Dusty shelves line the walls from floor to ceiling, packed with jars of preserved herbs and bundles of dried mushrooms.  A single lantern flickers on a hook near the low doorway to the north.";
	set_long(longDescription);
	isLit = 1;
	set_exits( ([ "north" : ROOMS + "hallway" ]) );
	add_item("shelves", "Rough wooden shelves sag under the weight of countless jars and bundles.  They look like they have been here for decades.");
	add_item("lantern", "A battered brass lantern.  Its flame dances behind a cracked glass pane.");
}

int query_lit() {
	return isLit;
}

void do_extinguish() {
	if (isLit == 1) {
		isLit = 0;
		write("You snuff out the lantern.  The room plunges into darkness.");
	} else {
		write("The lantern is already out.");
	}
}

Violations to Fix

There are 9+ violations hiding in this file:

  1. Missing #pragma strong_types as the very first line
  2. Tab characters used for indentation (should be 2-space indent)
  3. K&R bracket style (opening { on same line as statement)
  4. Missing return; at the end of void functions
  5. int used where status would be correct (true/false value)
  6. camelCase variable names instead of lowercase_underscore
  7. Lines exceeding 80 characters
  8. Missing ::create() call in create()
  9. Double-spacing between sentences in strings (should be single space)

File to create: exercises/ch11_codestyle/ex01_style_fix.c

Hints (click to reveal)
  1. Start at the very top of the file. What line must appear before everything else in every 3K .c file?
  2. Use your editor's "show whitespace" feature to spot tabs vs spaces. Every indentation level is exactly 2 spaces.
  3. Allman bracket style means the opening { goes on its own line, directly below the statement it belongs to. This applies to functions, if, else, for, while, and every other block.
  4. A status variable holds only 1 or 0 (true/false). If a variable is only ever set to 1 or 0 and tested as a boolean, its type should be status, not int.

Requirements

  • Reformat the entire file to strict 3K codestyle
  • Do not change any game behavior (same name, level, stats, chats, etc.)
  • Fix all of the following style issues:
    • Mixed tabs/spaces: convert everything to 2-space indentation
    • Inconsistent indentation depths (4, 8, and random levels used)
    • K&R brackets: convert all to Allman style
    • Lines over 80 characters: wrap long strings and statements
    • Missing comments: add function-level comments and section headers
    • int used for boolean attack_mode: should be status
    • int return type on do_inspect: should be status
    • void on a separate line from function name in heart_beat
    • Multiple statements crammed onto single lines: split them
    • Double-spacing between sentences: convert to single spacing
    • Single-statement if/else should not have brackets
    • Add proper variable declarations section with comments
    • Add proper file structure order (pragma, include, inherit, globals, prototypes, create, init, other functions)

File to create: exercises/ch11_codestyle/ex02_reformat.c

Hints (click to reveal)
  1. Start with the file structure: #pragma, #include, inherit, then global variables with comments, then function prototypes, then functions in standard order (create, init, reset, others).
  2. For long strings, break them across multiple lines using LPC string concatenation (adjacent string literals auto-concatenate). Keep each piece under 80 characters total including indentation.
  3. Single-statement if/else blocks drop the brackets entirely in 3K style. The single statement just gets indented on the next line.
  4. The attack_mode variable is only ever 0 or 1, so it is a status type. Similarly do_inspect returns only 0 or 1, so its return type should be status.
